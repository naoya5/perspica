## 提案（効果の大きい順）

### 1. エンジンへの通信がディスクのキャッシュに残る（プライバシーとディスク）

- **今**: `YakuCore/EngineClient.swift:20`が`URLSession.shared`を使う。llama-serverからのストリーミング応答（訳文そのもの）が`~/Library/Caches/Yaku/`と`~/Library/Caches/dev.naoya.yaku/`の`Cache.db`と`fsCachedData/`に残る。**実測**で合計1,310件（2026-11-06から）。設定の「履歴とキャッシュを消す」の対象外で、増え続ける。
- **直し方**: 既定のセッションを`URLSession(configuration: .ephemeral)`にする（`ModelDownloader`はすでにそうしている）。あわせて、起動時か「消す」のときに上の2つのフォルダを消す。
- **確かめ方**: 一時的に`.ephemeral`にした版で、翻訳3回でも行数が798 → 798のまま（`.shared`では1回ごとに +2）。**実測**。CPUは12.73〜13.13% で変わらない。**実測**。これは性能ではなく、プライバシーの修正。

### 2. エンジンの見張りが0.5秒ごとにプロセスを作る（アイドルCPU）

- **今**: `System/EngineWatchdog.swift`のシェルが`while kill -0 …; do …; sleep 0.5; done`を回す。エンジンが動いている間（最後の翻訳から既定で10分）ずっと、毎秒2回`sleep`を起動する。
- **コスト**: 同じ形のループを30秒動かしてCPU 0.29秒、1コアの約1.0%。**実測**（レプリカ）。SPEC 14章のアイドルの目標0.3% の3倍。`measure_cpu.py`はYakuのpidしか見ないので、今の表には出ない。
- **直し方**: ポーリングをやめる。アプリがパイプの書き込み側を持ち、見張りは`{ cat >/dev/null; kill -TERM "$server_pid"; } & wait "$server_pid"`で待つ。アプリが終わればパイプがEOFになり、サーバーが終われば`wait`が返る。
- **確かめ方**: エンジンが動いたまま60秒置き、見張りのシェルとその子のCPU時間を合計する（`/usr/bin/time`でくるむか、`ps -o cputime`を前後で読む）。

### 3. どこかでドラッグするたびにペーストボードを読む（ドラッグ中のCPU）

- **今**: `App/AppDelegate.swift:475`のグローバル監視は常に動いている。システムのどこかで`leftMouseDragged`が来るたびに、`handleIconDrag()`（:553）が`NSPasteboard(name: .drag).types`を読む。文字を選ぶ・窓を動かすだけでも呼ばれる。
- **コスト**: 1回0.81〜1.24 ms。**実測**（3回、マイクロベンチ）。`changeCount`も0.90〜1.16 msで、安くならない。毎秒120回のドラッグなら、メインスレッドで1コアの約10%。**推測**（回数を掛けただけ）。
- **直し方**: 先に、カーソルがメニューバーのアイコンの枠の近くにあるかを見る（ペーストボードを読まない、安い判定）。近いときだけ`types`を読む。
- **確かめ方**: パネルを閉じたまま、ほかのアプリで20秒ドラッグし続けて、`measure_cpu.py`で前後を比べる（人の手が要る）。

### 4. 訳している最中の13% の内訳（訳す間のCPU）

- 文字の出現（reveal）をなくすと9.90〜10.40%（3回）。revealのぶんは約3ポイント。**実測**。
- 刻みを30 Hz → 15 Hzにしても12.64〜12.95%。刻みの頻度を変えても効果はなかった。**実測**。
- 残りの約10% はまだ説明できていない。`sample`では`CoreGraphics`の`GRAYA8`系の画像処理（メイン）、`EngineClient.stream`の1バイトずつの読み取り（`EngineClient.swift:74`）、`LanguageCatalog.others`が描くたびに並べ替えるところ（`YakuCore/Language.swift:118`、computed property）が見えた。どれも割合は小さい。**推測**。
- **次に確かめること**: InstrumentsのTime Profilerで12秒取り、メインスレッドの残り10%を使っている処理を特定する。それまでは直さない。`LanguageCatalog.others`を`static let`にするのは、安全で小さいので先にやってよい。

### 5. PDF: 段落ごとにPythonを起動する（PDFの時間）

- **今**: `pdf-worker/translate_pdf.py:53`の`--clitranslator-command`は、段落1つごとに`paragraph_translator.py`を新しく起動する。そのたびに用語集を読み直し、HTTPの接続を作り直す。
- **コスト**: 1回の起動が約50 ms。**実測**（20回で1.00秒）。15ページ（235段落）では約12秒のCPU、4並列なら約3秒で、57.7秒のうち約5%。**推測**。
- **直し方**: pdf2zh-nextの翻訳器をプロセスの中で登録するか、常駐する翻訳器を1つ立てて接続と用語集を使い回す。`cache_prompt`と温度0は保ち、出力は1バイトも変えない。
- **確かめ方**: `app/tools/measure-pdf.sh`を5回走らせ、中央値を57.7秒と比べる。段落数235、エラー0であること。

### 6. 履歴の検索が古い履歴を見ない（正しさ）

- **今**: `Data/TranslationStore.swift:60`は最新の1000件を取ってから、メモリの中で絞る。保存は最大5000件（:13）。1001件目より古い一致は出ない。キーを1つ押すたびに1000件を取り直す。**コード**。
- **直し方**: SwiftDataの`#Predicate`と`localizedStandardContains`で検索をストアに任せ、入力を200 msほど待ってから検索する。

### 4の残り（約10%）について

Time Profiler（10秒）では、メインスレッドの1,110 msのうち約780 msにアプリのフレームがなかった。中身はSwiftUIのグラフ更新（`NSRunLoop.flushObservers`、390 ms）とAppKitの表示サイクル（`UC::DriverCore … stepTransactionFlush`、411 ms）。つまり、状態が変わる回数で決まっている。次の3つは試して効果がなかったので、元に戻した（どれも**実測**、3回ずつ）。

- 文字の出現の刻みを15 Hzにする: 12.6〜13.0%
- パネルの影を外す: 12.4〜13.2%
- パネルの`NSHostingView.sizingOptions = []`: 12.2〜13.1%

翌日（11-09夕方）に追加で調べたこと。

- run loopのイベントを数えると、翻訳中のメインスレッドは毎秒163回起きていた（**実測**、10秒）。reveal（30 Hz）と300 msごとの更新だけなら35回ほどのはず。
- 1つずつ届く断片をMainActorで受け取っているのが原因と考えて、ストリームをメインの外（`@concurrent`）で読み、最初の1片と300 msごとにだけメインへ戻す形にした。前の版と交互に4回ずつ測って、前12.6〜13.5% / 後12.8〜15.5%（**実測**）。効果がなかったので元に戻した。起きる回数が減ったかどうかは、2回目の記録が保存されずに確かめられていない。
- SwiftUI Instrumentsの表は、別のbundle ID（`dev.naoya.yaku.profile`、ad-hoc署名、`get-task-allow`）で包んで`--launch`しても空だった。run loopと表示更新の表だけが取れる。
- 測った時間帯はload averageが7〜87で、Chromeのプロセス3つが95% ずつ回っていた。`LanguageCatalog.others`の効果（約0.25ポイントの見込み）は、この揺れより小さく、CPU % では示せない。

`--demo-state translating`は約1秒ごとに翻訳をやり直すループで、やり直しのたびに文を消して流し直す。利用者が1文を訳すときの負荷とは形が違う。次の一手は、何の状態が何回変わっているかをSwiftUI Instrumentsで数えること。ただし`--attach`では何も記録されず、`--launch`は利用者のアプリを起動してしまう。別のbundle IDで包んだrelease版を作ってから測る。
