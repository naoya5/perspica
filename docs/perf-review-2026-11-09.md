## 提案（効果の大きい順）

### 1. エンジンへの通信がディスクのキャッシュに残る（プライバシーとディスク）

- **今**: `YakuCore/EngineClient.swift:20` が `URLSession.shared` を使う。llama-server からのストリーミング応答（訳文そのもの）が `~/Library/Caches/Yaku/` と `~/Library/Caches/dev.naoya.yaku/` の `Cache.db` と `fsCachedData/` に残る。**実測**で合計 1,310 件（2026-11-06 から）。設定の「履歴とキャッシュを消す」の対象外で、増え続ける。
- **直し方**: 既定のセッションを `URLSession(configuration: .ephemeral)` にする（`ModelDownloader` はすでにそうしている）。あわせて、起動時か「消す」のときに上の 2 つのフォルダを消す。
- **確かめ方**: 一時的に `.ephemeral` にした版で、翻訳 3 回でも行数が 798 → 798 のまま（`.shared` では 1 回ごとに +2）。**実測**。CPU は 12.73〜13.13% で変わらない。**実測**。これは性能ではなく、プライバシーの修正。

### 2. エンジンの見張りが 0.5 秒ごとにプロセスを作る（アイドル CPU）

- **今**: `System/EngineWatchdog.swift` のシェルが `while kill -0 …; do …; sleep 0.5; done` を回す。エンジンが動いている間（最後の翻訳から既定で 10 分）ずっと、毎秒 2 回 `sleep` を起動する。
- **コスト**: 同じ形のループを 30 秒動かして CPU 0.29 秒、1 コアの約 1.0%。**実測**（レプリカ）。SPEC 14 のアイドルの目標 0.3% の 3 倍。`measure_cpu.py` は Yaku の pid しか見ないので、今の表には出ない。
- **直し方**: ポーリングをやめる。アプリがパイプの書き込み側を持ち、見張りは `{ cat >/dev/null; kill -TERM "$server_pid"; } & wait "$server_pid"` で待つ。アプリが終わればパイプが EOF になり、サーバーが終われば `wait` が返る。
- **確かめ方**: エンジンが動いたまま 60 秒置き、見張りのシェルとその子の CPU 時間を合計する（`/usr/bin/time` でくるむか、`ps -o cputime` を前後で読む）。

### 3. どこかでドラッグするたびにペーストボードを読む（ドラッグ中の CPU）

- **今**: `App/AppDelegate.swift:475` のグローバル監視は常に動いている。システムのどこかで `leftMouseDragged` が来るたびに、`handleIconDrag()`（:553）が `NSPasteboard(name: .drag).types` を読む。文字を選ぶ・窓を動かすだけでも呼ばれる。
- **コスト**: 1 回 0.81〜1.24 ms。**実測**（3 回、マイクロベンチ）。`changeCount` も 0.90〜1.16 ms で、安くならない。毎秒 120 回のドラッグなら、メインスレッドで 1 コアの約 10%。**推測**（回数を掛けただけ）。
- **直し方**: 先に、カーソルがメニューバーのアイコンの枠の近くにあるかを見る（ペーストボードを読まない、安い判定）。近いときだけ `types` を読む。
- **確かめ方**: パネルを閉じたまま、ほかのアプリで 20 秒ドラッグし続けて、`measure_cpu.py` で前後を比べる（人の手が要る）。

### 4. 訳している最中の 13% の内訳（訳す間の CPU）

- 文字の出現（reveal）をなくすと 9.90〜10.40%（3 回）。reveal のぶんは約 3 ポイント。**実測**。
- 刻みを 30 Hz → 15 Hz にしても 12.64〜12.95%。刻みの頻度は効いていない。**実測**。
- 残りの約 10% はまだ説明できていない。`sample` では `CoreGraphics` の `GRAYA8` 系の画像処理（メイン）、`EngineClient.stream` の 1 バイトずつの読み取り（`EngineClient.swift:74`）、`LanguageCatalog.others` が描くたびに並べ替えるところ（`YakuCore/Language.swift:118`、computed property）が見えた。どれも割合は小さい。**推測**。
- **次の一手**: Instruments の Time Profiler で 12 秒取り、メインスレッドの残り 10% の持ち主を特定する。それまでは直さない。`LanguageCatalog.others` を `static let` にするのは、安全で小さいので先にやってよい。

### 5. PDF: 段落ごとに Python を起動する（PDF の時間）

- **今**: `pdf-worker/translate_pdf.py:53` の `--clitranslator-command` は、段落 1 つごとに `paragraph_translator.py` を新しく起動する。そのたびに用語集を読み直し、HTTP の接続を作り直す。
- **コスト**: 1 回の起動が約 50 ms。**実測**（20 回で 1.00 秒）。15 ページ（235 段落）では約 12 秒の CPU、4 並列なら約 3 秒で、57.7 秒のうち約 5%。**推測**。
- **直し方**: pdf2zh-next の翻訳器をプロセスの中で登録するか、常駐する翻訳器を 1 つ立てて接続と用語集を使い回す。`cache_prompt` と温度 0 は保ち、出力は 1 バイトも変えない。
- **確かめ方**: `app/tools/measure-pdf.sh` を 5 回走らせ、中央値を 57.7 秒と比べる。段落数 235、エラー 0 であること。

### 6. 履歴の検索が古い履歴を見ない（正しさ）

- **今**: `Data/TranslationStore.swift:60` は最新の 1000 件を取ってから、メモリの中で絞る。保存は最大 5000 件（:13）。1001 件目より古い一致は出ない。キーを 1 つ押すたびに 1000 件を取り直す。**コード**。
- **直し方**: SwiftData の `#Predicate` と `localizedStandardContains` で検索をストアに任せ、入力を 200 ms ほど待ってから検索する。

### 4 の残り（約 10%）について

Time Profiler（10 秒）では、メインスレッドの 1,110 ms のうち約 780 ms にアプリのフレームがなかった。中身は SwiftUI のグラフ更新（`NSRunLoop.flushObservers`、390 ms）と AppKit の表示サイクル（`UC::DriverCore … stepTransactionFlush`、411 ms）。つまり、状態が変わる回数で決まっている。次の 3 つは試して効かなかったので、元に戻した（どれも**実測**、3 回ずつ）。

- 文字の出現の刻みを 15 Hz にする: 12.6〜13.0%
- パネルの影を外す: 12.4〜13.2%
- パネルの `NSHostingView.sizingOptions = []`: 12.2〜13.1%

翌日（11-09 夕方）に追加で調べたこと。

- run loop のイベントを数えると、翻訳中のメインスレッドは毎秒 163 回起きていた（**実測**、10 秒）。reveal（30 Hz）と 300 ms ごとの更新だけなら 35 回ほどのはず。
- 1 つずつ届く断片を MainActor で受け取っているのが原因と考えて、ストリームをメインの外（`@concurrent`）で読み、最初の 1 片と 300 ms ごとにだけメインへ戻す形にした。前の版と交互に 4 回ずつ測って、前 12.6〜13.5% / 後 12.8〜15.5%（**実測**）。効かなかったので元に戻した。起きる回数が減ったかどうかは、2 回目の記録が保存されずに確かめられていない。
- SwiftUI Instruments の表は、別の bundle ID（`dev.naoya.yaku.profile`、ad-hoc 署名、`get-task-allow`）で包んで `--launch` しても空だった。run loop と表示更新の表だけが取れる。
- 測った時間帯は load average が 7〜87 で、Chrome のプロセス 3 つが 95% ずつ回っていた。`LanguageCatalog.others` の効果（約 0.25 ポイントの見込み）は、この揺れより小さく、CPU % では示せない。

`--demo-state translating` は約 1 秒ごとに翻訳をやり直すループで、やり直しのたびに文を消して流し直す。利用者が 1 文を訳すときの負荷とは形が違う。次の一手は、何の状態が何回変わっているかを SwiftUI Instruments で数えること。ただし `--attach` では何も記録されず、`--launch` は利用者のアプリを起動してしまう。別の bundle ID で包んだ release 版を作ってから測る。
