### 3.3 PDF の処理中でもパネルの翻訳は止まらない（SPEC 7.3）

15 ページの仕事を走らせたまま、起動 60 秒後にパネルの翻訳（1,939 文字 / 4 つの塊）を始めた。**PDF の段落を訳している最中**（worker が 18:26:34 に走り出し、出力が 18:28:17）に重なっている。

| 項目 | 結果 |
|---|---|
| 最初の文字まで | **0.140 秒**（実際に訳し直した 2 本目は 0.032 秒） |
| 4 つの塊を訳し終わるまで | 3.572 秒 |
| 待たされた感じ | なし。パネルは普通に文字が出た |

```
translate start id=34943A9F surface=panel chars=1939 chunks=4 … glossary=1 model=0.8b
translate first piece id=34943A9F surface=panel in 0.140s
translate start id=6AEA4779 surface=panel chars=1939 chunks=4 …
translate first piece id=6AEA4779 surface=panel in 0.032s
translate done id=6AEA4779 in 3.572s pairs=4
```

理由は 2 つ。エンジンは `--parallel 4` で動いていて、pdf2zh-next 側を `--pool-max-workers 3` に絞ってあるので、**パネルの分の 1 つが必ず空いている**。そして `EngineManager.beginPDFWork()` が仕事の間だけ idle の見張りを止めるので、PDF の最中にエンジンが落ちない。

```
engine: PDF work started (count=1); idle stop suspended
…（仕事の間）
engine: PDF work finished; idle stop resumed
```

### 3.8 ログとコードで経路を確かめたもの

| 仕様 | どう通っているか |
|---|---|
| 入口 5 つ（SPEC 8.1） | ①メニューバーのアイコンにファイルをドラッグ（`NSPasteboard(.drag)` を見て、アイコンの枠の上ならパネルをドロップ状態で開く）②パネルへのドロップ（`registerForDraggedTypes([.fileURL])`）③管理画面の PDF のページ ④島へのドロップ ⑤Finder の「このアプリで開く」（`CFBundleDocumentTypes` → `application(_:open:)`）とパネルの「PDF を開く…」（⌘O）。**5 つとも同じ `PDFQueue.enqueue` を通る** |
| 1 つずつ（SPEC 8.1） | `startNextIfIdle()` は `runningID` があると何もしない。列は古い順に取る（`jobs.reversed().first { $0.jobState == .queued }`） |
| 元のフォルダに出す（SPEC 8.3） | `PDFOutputLocation.destinationDirectory`（元のフォルダが書けるなら そこ → 設定のフォルダ → `~/Downloads`） |
| 出力を開く（SPEC 8.3） | 設定の「訳し終わったら開く」が入っていれば `NSWorkspace.open`。パネルが閉じていれば通知（`UNUserNotificationCenter`、カテゴリ `YAKU_PDF_DONE`、`開く`） |
| 島の見え方（SPEC 4.5） | `NotchController.setUp(enabled:force:)` は「設定がオン」かつ「ノッチのある画面がある」ときだけ作る。デモの `force` はメイン画面に描く。位置は `screen.frame.midX - 320` / `maxY - 520`、窓の高さ 520。この Mac の内蔵ディスプレイにはノッチがあり（`notch=(179.0, 32.0)`）、島はその上に出る（`notch: island at (-1055.0, 920.0, 640.0, 520.0)`。内蔵ディスプレイがメインの左にある配置なので x は負になる） |
| 上の耳（SPEC 4.5） | `NotchModel.earRadius` を「閉じているときは 6、開いたら島の高さに応じて 6〜14」にした。試作は 6 の固定で、島が背が高くなると耳が小さな突起に見えた。**見た目は未確認**（3.9） |
| 段階名（SPEC 8.2） | BabelDOC が返す段階名をそのまま `PDFStage.japaneseName` に通す。知らない名前も「処理中」になる |
| API キー（SPEC 8.2） | コマンドラインには出さず `YAKU_ENGINE_API_KEY` で渡す。ログの引数にも出ていない（3.2 の `worker started` の行に `--api-key` は無い） |
| ドキュメントの題を文脈に | `--context` に PDF の題（メタデータ、無ければファイル名）を渡す。3.2 のログは `--context attention` |

## 4. 仕様との違い・できなかったこと

### 4.1 画面がロックされていて、撮影と CPU の計測ができなかった（一番大きい）

M2 のときと同じで、**この作業の間ずっと** `CGSSessionScreenIsLocked = 1` だった。M1 の撮影はできている（`M1-panel-*.png`）ので、M2 の途中から誰かがロックしたままになっている。指示は「ロックが解けるのを待たずに進め、撮影と計測は仕組みだけ用意しておく」だったので、そうした。

できなかったこと:

- M3 の 30 枚の撮影（3.9）。**1 枚も撮れていない**
- SPEC 14 章の計測のうち、PDF の仕事中・島の作業中の CPU とメモリ。ロック中はアプリが描かれないので `0.00%` にしかならない
- M2 の 40 枚の撮影と計測（M2.md 3.8・3.9 のまま）

用意したこと: `tools/capture-m3.sh` と `tools/measure-m3.sh`。**画面のロックを外してから、M2 → M3 の順に走らせる。**

### 4.2 `~/Downloads` への落ち方は動かしていない

`PDFOutputLocation` は「元のフォルダが書けない → 設定のフォルダが書けない → `~/Downloads`」の順に決める。この作業で書いてよい場所に `~/Downloads` が入っていないので、**実際に落とすところは動かしていない**（コードとログの文言だけ）。書けないフォルダを渡す確認は親の判断で。

### 4.3 島の上の耳は直したが、見てはいない

`earRadius` を島の高さに合わせて 6〜14 にした。理由は「試作の 6 の固定だと、島が背高になったときに、画面の上端と島の間の丸みが小さな黒い突起に見える」というもの。**ロック中で見られないので、直ったかどうかは分からない。** 親が撮った `M3-notch-*.png` で見てほしい。

### 4.4 段落ごとの翻訳に履歴（history）を渡していない

SPEC 7.4 の「直前の 2 組を履歴にする」はパネル・HUD・管理画面の話で、PDF は段落が独立しているので渡していない。そのぶん文脈は「PDF の題 + 用語集 + 文体」だけになる。段落の並びを保ちたければ `--pool-max-workers 1` にする手もあるが、15 ページで 90 秒が数倍になるので採らなかった。

### 4.5 部品の取得は「初めての PDF のとき」に聞く

SPEC 8.2 のとおり、設定の PDF タブからも入れられるようにしてある（`取得する`）。950MB と数分かかるので、**先に入れておきたい人は設定から入れる**。`--demo-pdf` は人操作なしで通すため、質問を飛ばして取得を始める。

### 4.6 `--pdf-python` は開発の抜け道

SPEC 8.2 は「アプリが `uv` で入れる」としている。それとは別に、試作の `lab/plamo-pdf-translate/.venv/bin/python` を使えるように `--pdf-python <path>` と設定の欄を足した。**この記録の 3.2〜3.6 はこの抜け道で走らせた**（3.4 だけが本物の取得）。仕様には無いので記録しておく。

## 5. 気づいたこと・仕様に足したほうがよさそうなこと

- **撮影と計測は「画面のロックを解いた状態」が前提**（M2 の 4.1 と同じ）。段階の確認を始める前にロックを外す、と SPEC 15 章に書いておくとよい。**2 段階続けて撮れていない**
- **部品の大きさは 957MB**（`pdf2zh-next==2.9.0` + `bitstring<5`、132 個）。SPEC 13 章の「約 ___MB」を実測に合わせて「約 950MB」にした。仕様に数字を書くならこの値で
- **15 ページが 92.9 秒**（試作 89.96 秒）。SPEC 15 章の「120 秒以内」に収まっている。**この時間はモデルの 0.8B のときのもの**で、2B / 8B では別に測る必要がある
- **PDF の最中のパネル翻訳は 0.14 秒で最初の文字が出た**（SPEC 7.3 の「止まらない」）。効いているのは `--parallel 4` と `--pool-max-workers 3` の組み合わせなので、**この 2 つの数字は仕様に書いておくとよい**（片方だけ変えると成り立たなくなる）
- **PDF の仕事の間は idle でエンジンを止めない**（`beginPDFWork` / `endPDFWork`）。SPEC 7.1 の「アイドルで止める」との関係を 1 行足しておくとよい
- **出力名の「 (2)」は元の名前に対して**付く（`attention.ja (2).pdf`）。`attention (2).ja.pdf` ではない。SPEC 8.3 の読み方として記録しておく
- 段落ごとの翻訳は**アプリと同じ PFML3 を Python 側でも組んでいる**（`paragraph_translator.py`）。2 か所に同じ書式があるので、**片方を直したらもう片方も直す**必要がある。PFML3 の書式は `YakuCore/PFML3.swift` を正とする
- `--demo-pdf` は `--demo-quit-after` と組で使う。仕事が終わっても窓は開いたままなので、デモの最後に自分で終わる
