## 2. F4: 箇条書きの折り返しが切れ端で訳されていた

### 2.1 何が起きていたか（利用者のログ、実測）

`~/Library/Logs/Yaku/app.log` の 2026-11-08T10:33:52Z の実行（外部モニター 1×、
2560×1440、選択した領域 1107×459pt）:

```
overlay: block 3 whole frame=929x16 lineHeight=18.5 (box 16.0) lines=1 bold=no • Briefs each agent. …
overlay: block 4 whole frame=68x12  lineHeight=12.0 (box 12.0) lines=1 bold=no the work.
overlay: block 5 whole frame=831x16 lineHeight=18.4 (box 16.0) lines=1 bold=no • Keeps agents moving. …
overlay: block 6 whole frame=971x16 lineHeight=18.4 (box 16.0) lines=1 bold=no • Keeps you informed. …
overlay: block 7 whole frame=92x14  lineHeight=18.0 (box 14.0) lines=1 bold=no one outcome.
```

`block 4` は `the work.` だけ、`block 7` は `one outcome.` だけで、それぞれ
「作業。」「一つの結果。」と訳されていた。**原因は 3 つあり、すべて直した。**

### 2.2 原因 1: 短い折り返し行は枠が 3 分の 1 短い

`• Keeps you informed. …` の枠は 971×16、その続きの `one outcome.` は 92×14。
`one outcome.` には上に伸びる字（ascender）も下に伸びる字（descender）も無いので、
Vision の枠が 12.5% 低くなる。`OCRBlockBuilder.heightTolerance` は 25% なので
ぎりぎり通るはずだが、`block 4` は 12.0 対 18.5 で **35%** 離れていた。

つまり、**墨から大きさが取れずに Vision の枠の値に戻っていた**。枠の 12.0 と、
隣の行の墨から測った 18.5 が、M5.2 の大きさの規則（8%）で比べられ、
「別の行だ」と判定されていた。枠の値と墨の値は**同じ単位ではない**のに、
同じ土俵で比べていた。

### 2.3 原因 2: 墨の判定が、枠の明暗の当て推量で裏返っていた

`TextInk` と `OverlayEmphasis` は、墨かどうかを

```swift
let darkText = background > 0.5
let threshold = background + (darkText ? -inkContrast : inkContrast)
```

で決めていた。枠の**中央値**が 0.5 より明るいかで「暗い字」と決め打ちする。
短い行を切り詰めた枠は**墨が半分以上を占める**ことがあり、その中央値は
文字の明るさの側に寄る。すると当て推量が裏返り、**墨が 1 つも見つからない**。
墨が無ければ大きさは nil になり、呼び出し側は Vision の枠に戻る。これが 2.2 の
「戻った値」を作っていた。

直しは、**明暗の当て推量をやめて、中央値から上下どちらに離れていても墨と数える**
こと。`TextInk.isInk` に 1 か所だけ置き、`bandHeight` / `inkWidth` /
`OverlayEmphasis.inkRatio` がそれを使う。当て推量が正しかった場所では同じ判定に
なるので、M5 で合わせた帯の定数はそのまま使える。

### 2.4 原因 3（本命）: 折り返しを、枠ではなく**文**で見る

上の 2 つを直しても、**枠が 35% 違う**こと自体は変わらない。実画面では
`one outcome.` の枠が本当に 14 で、上の行が 16 だからだ。枠だけを見る限り
「別の行」である。

そこで `OCRBlockBuilder.continuesSentence` を足した。人が読むときの規則そのもの:

- 上の行が文の終わり（`.` `!` `?` `:` `;` `。` `！` `？` `：` `；` `…`）で終わっておらず、
  閉じ記号（`"` `)` `」` など）が続いていても文末とみなし、
- 下の行が**小文字で始まる**なら、その文はまだ続いている。
- `•` `-` `1.` `2)` などで始まる行は新しい項目なので、続きではない。

この行は高さの規則・字下げの規則・2 つの分割規則（`lineLengthRatio` と
`sizeTolerance`）を**すべて免除**する。枠に基づく規則はすべて Vision の枠を
根拠にしており、枠より文のほうが確かな証人だからだ。日本語には大文字小文字が
無いのでこの規則は決して発火せず、CJK でよく効く高さの規則がそのまま判定する。

字下げ（ぶら下げ）も同じ規則の中で見る: 続きの行が上より右にずれていても、
ずれが**行の高さの 4 倍以内**なら同じ段落とする。箇条書きの 2 行目は記号の分だけ
右に寄るため、`alignmentRatio`（0.5 倍）だけでは「そろっていない」と読まれる。

**この規則の代償（正直に）**: 折り返しと見なすと**大きさの規則も `lineLengthRatio`
も免除される**ので、大きさを間違って読んだ行が切れ端になることは二度と無い。その
代わり、**小文字で始まる短い行が上の見出しに付いてしまう**。たとえば UI の行
`Lock Screen` の下に `recent items and notifications` とだけ書かれていると、下の行は
小文字で始まり、左端もそろっているので**同じブロックにまとまる**（`follows` の
`aligned` は通る。`hanging` は 3 つの選択肢の 1 つにすぎず、字下げは必須ではない）。

見本 6 つでは起きていない（2.7）。`ui.png` の行は見出しも説明も**大文字で始まる**ため
（`("Enable notifications", "Show a banner when a job finishes")` など）、下の行が
小文字で始まるという条件を満たさない。実際の macOS の設定画面も説明は大文字始まりが
多いので risk は小さいが、小文字で始める画面では消えない。測れていない画面での risk
として残す。

## 4. PDF（F3）

### 4.1 訳文の字体が明朝になっていた

利用者の出力 `ARMS-Agentic-OS-Guide.ja.pdf` の訳文は
`SourceHanSerifJP-Regular` で描かれていた。元の PDF は幾何学的な sans だ。

`pdf2zh-next` には `--primary-font-family serif|sans-serif|script` がある。
指定しないと BabelDOC が**元のフォントの `is_serif` フラグから 1 文字ずつ**選ぶ。
この説明書の本文は **Type 3** フォントで描かれており、Type 3 にはフォント記述子が
無い。`pymupdf` はそれでも答えるが、その答えは**列挙型の既定値**であって
文書から読んだ値ではない。実測すると本文のフォントは `is_serif=True` を返す。
これが明朝に落ちた理由だ。

直しは `pdf-worker/pdf_font_family.py`。元の PDF のフォントを 2 つの証拠で読み、
**文字数で重み付け**して決める:

1. フォント記述子の `is_serif`（Type 3 と読めないフォントは**証拠なし**として捨てる）、
2. フォントの**名前**（`Times` `明朝` → serif、`Helvetica` `Doto` `角ゴ` → sans）。

どちらも何も言わないときは **sans-serif**。この説明書がまさにその場合で、
画面向けの文書と日本語の訳文はどちらもゴシックのほうが読みやすい。

測定（この説明書、本文の Type 3 フォントは証拠なし）:

| 文書 | 証拠 | 選んだ字体 | 訳文のフォント（実測） |
|---|---|---|---|
| `ARMS-Agentic-OS-Guide.pdf` | serif 0 字 / sans 104 字 / **不明 24584 字** | `sans-serif` | `SourceHanSerifJP-Regular` → **`SourceHanSansJP-Regular`** |
| `Times-Roman` で描いた 1 ページ | serif 1152 字 | `serif` | （論文は明朝のまま） |
| `Helvetica` で描いた 1 ページ | sans 1152 字 | `sans-serif` | |
| `Courier` で描いた 1 ページ | 等幅なので判断しない | `sans-serif`（既定） | |

### 4.2 字間を空けた大文字のラベル

親の指示は「モデルがラベルを壊すので、訳さずに返すか BabelDOC の設定を探せ」だった。
**測ると、前提が 2 つとも違っていた。** 直せたのは字体までで、字間は直っていない。

#### (a) モデルは壊していない

ラベルは**モデルに届いている**。`~/.cache/pdf2zh_next/cache.v1.db` を、下に書くラベルの
形（90 文字以下・小文字なし・字間型か 2〜8 語）でふるいにかけると 1698 段落中 61 件が
該当し、**そのうち 60 件はモデルがそのまま返している**。唯一の変化は
`S TA R T H E R E` → `S T A R T H E R E` という**間隔の正規化**で、文字は失っていない。

| | 件数 |
|---|---|
| ラベルと判定した段落（キャッシュ内） | 61 |
| モデルが**そのまま**返した | **60** |
| モデルが変えた | 1（`S TA R T H E R E` → `S T A R T H E R E`、間隔の正規化） |

親が挙げた `STARTHEEE` は**この文書のキャッシュに存在しない**（`STARTHEEE` で検索して
0 件）。利用者の出力にも無く、実際は `STARTHERE`（間隔が落ちただけ）になっている。
親が見た例は別の版か別の PDF のものと思われる。

#### (b) 字間を潰しているのは BabelDOC のテキスト取り出し

`get_char_unicode_string` は、字間を空けたラベルの**隣り合う 1 文字ごとに空白を 1 つ**
入れて取り出す。すると `P A R T␣␣1␣O F␣␣4`（語間は 2 つ）と
`P␣A␣R␣T`（字間は 1 つ）の区別が消え、組み直しでは**すべての隙間が同じ幅**で描かれる。

その結果、**字間は残り、語間だけが落ちる**:

| | 元 | 出力 |
|---|---|---|
| 表紙のラベル | `A R O B O N U G G E T S G U I D E` | `AROBONUGGETSGUIDE`（字間は残る） |
| 3 ページ | `P A R T  1  O F  4  ·  B O T T O M - U P  O R D E R` | `PART1OF4 · BOTTOM-UPORDER` |

字の幅は `docs/checks/shots/M6-pdf-partlabel-*.png` の 3 枚で見える
（ORIGINAL 11.89px → BEFORE 8.71px → AFTER 8.09px と、組み直しで詰まる）。
`START HERE` の `S T A R T H E R E` は**文字が欠けていない**ことも同じ方法で確かめた。
`babeldoc` / `pdf2zh-next` にこれを止める露出済みの設定は無い
（`formular_char_pattern` / `formular_font_pattern` は段落単位なので、見出しと同じ
段落に居るラベルには使えない）。

**まだ試していない道（正直に）**: `translate_pdf.py` はすでに `babeldoc` の内部を
触っている（`babeldoc.assets.assets` を import して温める、`translate_pdf.py:103`）ので、
`get_char_unicode_string` を**差し替えて**文字の x 座標から語間を復元する道は
残っている。今回は**やっていない**。理由は 2 つ:

1. この関数は BabelDOC の版面組みの中心にあり、差し替えると**他のすべての段落の
   組み方に触れる**。M6 の他の変更と違って、影響範囲を測り切れない。
2. 正しく直すには「同じ文字幅で並ぶ 1 文字の並び」と「語の切れ目」を**座標から**
   見分ける規則が要る。字間と語間はどちらも空白 1 文字に潰れているので、元の
   グリフ位置を読み直す必要がある（`get_char_unicode_string` はそれを捨てている）。

**次にやるなら**: `pdf_font_family.py` と同じ形で「元の PDF から字間を読む」小さな
モジュールを書き、`babeldoc` の該当関数をそこへ向ける。M6 の範囲では、露出済みの
設定（親が挙げた 2 つの道）を先に試して、どちらも効かなかったところまでで止めた。

#### (c) 試したこと: ラベルをそのまま返す（`is_label`）→ **戻した**

親の指示どおり `paragraph_translator.py` に `is_label` を足した（90 文字以下・小文字
なし・字間型か 2〜8 語）。キャッシュ 1698 段落で 61 件が該当し、**誤検出（小文字を
含むもの）は 0 件**だった。

だが**出力は 1 バイトも変わらなかった**。ラベルを含むページを前後で比べると:

```
AROBONUGGETSGUIDE / README / STARTHERE / PART1OF4 / PART2OF4 / RECAP
  → 出現ページが前後で完全に一致（SAME）
```

モデルがすでにそのまま返しているので、**エコーは何も直さない**。bug-fix playbook の

### 4.5 訳の質は落ちていないか（速くした代償の確認）

親の条件は「質を落とさずに 2 割以上速く」。上の 235 段落の表は**段落数と誤り数**
しか見ていないので、**訳文そのものを比べた**。

違えばそれは同時実行が訳文を変えた証拠になる。

|---|---|

| qps 24 対 qps 24（もう 1 回） | **422 / 422（100.0%）** |

**qps 24 の出力は qps 3 と 1 文字も変わらない。** 同じ qps 24 を 2 回走らせても
同じなので、この一致は偶然ではない（エンジンが決定的であることも同時に確かめた）。
同時実行で訳文が変わることは、この測り方では**起きていない**。

段落数は 33（両方）、誤りは 0（両方）。qps 3 が 22.73 秒、qps 24 が 16.01 秒。

**限界**: 見たのは 3 ページ・33 段落で、しかも**このエンジンとこのモデル**で。
質を測ったのは「速くしても訳文が変わらない」ことで、「訳文が正しい」ことではない
（それは M6 の範囲外で、M5 までの品質の話）。

**戻して失ったもの（正直に）**: ラベルのエコー（4.2(c)）は、モデルへ行く**24 段落を
0.24 秒ずつ早く返す**ので、**約 5 秒（final の 9%）速かった**（回 1〜3 の中央値 52.66 秒

それでも戻したのは、**「ラベル」と「大文字の見出し」を区別できない**ためで、
`TABLE OF CONTENTS` のような見出しを訳さずに残す恐れがある（利用者の 2 文書 1698
段落では 0 件だったが、測れていない文書での risk）。**9% が要るなら戻せる**。

**確かめたこと（benchmark-checklist の 4 と 7）**: ハーネスは毎回**段落数と
キャッシュ当たり数と誤り数**を出す。両側とも 235 段落、誤り 0、キャッシュ当たり
22〜25（同じ文書を何度も訳した分の重複で、意図したもの）。「速いが何もしていない」
run はここで捕まる。
